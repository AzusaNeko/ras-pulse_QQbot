# Bark 手机推送设计检查点

## 状态

需求访谈与本地实现已完成，OpenSpec 变更 `add-bark-mobile-notifications` 已通过严格校验；单元测试、类型检查和生产构建通过，真实 iPhone/APNs 验收尚未执行。本文记录已经确认的决策及其理由。

## 已确认决策

### Bark 推送的事件范围

Bark 手机推送同时覆盖以下事件：

- 监控关键词发现新商品或识别到旧商品更新。
- 收藏商品发生降价或售出变化。

理由：手机推送用于用户离开电脑后的提醒，应与现有桌面通知的事件范围保持一致，避免收藏商品状态变化只能在电脑端看到。

### Bark 推送独立启停

Bark 手机推送使用独立的 `barkEnabled` 开关，并且默认关闭。现有 `notificationsEnabled` 继续只控制桌面通知。

理由：用户可能只需要手机推送或只需要电脑弹窗；未完成 Bark 配置时默认关闭，也可以避免持续产生无效发送和错误日志。

### 支持多个 Bark 设备

首版支持配置多个 Bark 设备。每台设备独立保存设备名称、启用状态和 `deviceKey`，并可单独发送测试通知。

理由：存在同时向多台 iPhone 推送的实际使用场景。如果首版只保存单个 `deviceKey`，后续升级为多设备会同时影响持久化结构、设置界面、密钥保护、测试操作和部分发送失败的处理，因此应从首版采用设备列表模型。

### 向启用设备广播相同消息

首版不提供设备级关键词或事件过滤。每次产生 Bark 手机推送时，所有已启用且配置有效的 Bark 设备接收相同消息。

理由：当前需求是让多台 iPhone 共同接收煤炉产生的手机提醒。设备级过滤会引入另一套订阅关系，以及收藏变化归属、关键词变更同步等额外规则；在没有实际需求前不扩大范围。

### 使用一个可配置的 Bark Server

全局只配置一个 Bark Server 地址，默认值为 `https://api.day.app`，并允许用户改为自建服务器地址。所有 Bark 设备的 `deviceKey` 必须属于当前配置的服务器。首版不支持不同设备分别连接不同 Bark Server。

理由：默认公共服务器可以开箱即用；允许修改服务器地址可以支持自建和隐私需求。单服务器模型能够避免跨服务器设备管理、批量请求差异和复杂的部分失败语义。

### 提供普通和时效性两个通知等级

Bark 使用一个全局通知等级，所有设备共用。首版只允许以下两个值：

- `active`：普通通知，也是默认值，遵守系统专注模式。
- `timeSensitive`：时效性通知；在用户于 iPhone 上授权后，可以在专注模式中显示。

首版不提供 `critical` 关键通知和 `call` 持续响铃能力。

理由：商品提醒可能存在时效性需求，但普通提醒不应默认越过专注模式。关键通知和持续响铃会越过静音或勿扰，干扰程度与当前商品提醒场景不匹配。

### Bark 商品图片独立控制

增加独立的 Bark 商品图片开关并默认开启，不复用桌面通知的图片开关。商品上新、旧商品更新和收藏商品变化均可将对应商品缩略图作为 Bark 的 `image` 媒体附件；图片获取或显示失败不得影响标题、正文和商品链接的推送。

理由：手机与桌面是两个独立通知通道，用户可能希望它们采用不同的图片策略。商品缩略图可以提高辨识度，但只属于辅助展示，不能成为通知成功的前置条件。

### 逐设备发送并进行一次有限重试

每台启用的 Bark 设备独立发送，单台设备失败不阻塞其他设备。发生网络错误、请求超时或 HTTP 5xx 时，等待两秒后最多重试一次；HTTP 4xx 不重试。不建立持久化重试队列，应用退出后不继续补发。

理由：短暂网络故障不应直接造成永久漏推，但响应丢失时重试可能产生重复通知。当前商品提醒更重视及时送达，因此接受极少数重复通知的可能性，同时通过单次重试限制重复和请求压力。

### 允许明文 HTTP 并展示安全警告

自建 Bark Server 地址允许使用 `http://`。设置页在检测到明文 HTTP 地址时必须明确提示：`deviceKey` 与通知内容会以明文方式传输。该提示不阻止保存、测试或正式发送。

理由：局域网、NAS 等自建环境常以 HTTP 提供服务，强制 HTTPS 会显著增加个人部署成本。由用户根据网络环境决定是否接受风险，同时确保风险在配置时可见。

### 首版不支持 Bark 内容加密

首版不生成 Bark `ciphertext`，也不管理通知内容加密算法、密钥或初始化向量。Bark `deviceKey` 仍须使用 Windows DPAPI 加密保存，默认服务器地址使用 HTTPS；用户可通过自建 Bark Server 降低公共服务器接触通知内容的风险。

理由：Bark 内容加密要求每台 iPhone 的 Bark App 配置完全匹配的算法和密钥，多设备场景会增加密钥同步、轮换及解密失败诊断成本。当前可通过本地密钥保护、HTTPS 和自建服务器满足首版安全需求，未来增加内容加密时无需改变业务侧调用方式。

### Bark 始终发送完整商品信息

Bark 不提供商品名称和价格的独立显示开关，也不复用桌面通知的对应开关。商品通知始终包含商品名称、价格、事件或变化摘要及可点击的 Mercari 商品链接；图片仍由 Bark 图片开关独立控制。

理由：手机提醒需要在不打开商品页面时提供足够的判断信息。隐藏名称或价格会显著降低提醒价值，而继续增加细分开关会使设置界面过于零碎。

### Bark 声音由接收设备管理

煤炉首版不增加 Bark 声音开关，也不主动指定 Bark `sound`。现有桌面通知声音开关继续只控制电脑；每台 iPhone 通过自身的 Bark App 或 iOS 通知设置决定是否响铃及使用什么声音。

理由：多台接收设备可能有不同的声音偏好，由设备本地管理可以避免一个全局设置覆盖所有手机，也减少与 iOS 静音、专注模式和 Bark 本地设置之间的冲突。

### 采用最小配置有效性规则

配置必须满足以下规则：

- Bark Server 必须是完整的 `http://` 或 `https://` 地址；空地址、其他协议和相对地址拒绝保存。
- 添加 Bark 设备时 `deviceKey` 不得为空。
- 同一 Bark Server 下不得重复添加相同的 `deviceKey`。
- 设备名称可以为空；为空时自动生成顺序名称。
- 不校验 `deviceKey` 的长度或字符格式，以兼容自建服务器。

理由：这些规则可以在发送前发现确定无效或必然产生重复通知的配置，同时避免根据公共服务器行为猜测并限制自建服务器的 Key 格式。
